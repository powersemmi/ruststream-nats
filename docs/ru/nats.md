# NATS {#nats}

`ruststream-nats` запускает сервис RustStream на NATS. У NATS две модели доставки, и крейт
покрывает обе. Core NATS отдаёт сообщение тем, кто подписан в этот момент, и не хранит ничего.
JetStream сохраняет его в стриме: это журнал, как у Kafka. Фича `testing` добавляет
внутрипроцессный транспорт NATS, поэтому сервис можно тестировать без сервера. Понятия фреймворка
(как писать подписчиков, маршрутизация, кодеки, middleware) описаны в
[документации RustStream](https://powersemmi.github.io/ruststream/).

```toml
[dependencies]
ruststream = { version = "0.7", features = ["macros", "json"] }
ruststream-nats = "0.7"
serde = { version = "1", features = ["derive"] }

[dev-dependencies]
ruststream-nats = { version = "0.7", features = ["testing"] }
```

## Какой glob импортирует файл {#which-glob-a-file-writes}

Файл с обработчиком пишет `ruststream::prelude::*` и ограничивает внедрённого издателя той
совместимостью, которая ему нужна (`Out<impl Publisher>`, `Out<impl RequestReply>`). Такое тело не
называет брокера, поэтому один и тот же обработчик без изменений монтируется и на настоящий сервер,
и на внутрипроцессный транспорт.

Файл с маршрутами пишет `ruststream_nats::prelude::*`. Прелюдия крейта реэкспортирует прелюдию
фреймворка и добавляет брокера этого крейта, два его дескриптора подписки и его политики
публикации. В точке монтирования имена у них одни и те же на любом брокере: `Publish` - это обычная
публикация на том транспорте, на который монтируется файл.

Сервис из одного файла - и то и другое, поэтому он берёт прелюдию брокера.

Прелюдию брокера берёт и один вид тела обработчика: то, которое задаёт настройку JetStream для
отдельного сообщения. См.
[что одно сообщение JetStream заявляет о себе](#what-one-jetstream-message-states-about-itself).

## Жизненный цикл {#the-lifecycle}

Три типа, по одному на каждое состояние соединения:

```text
NatsBroker::new(url)      только конфигурация, синхронно, без ввода-вывода
  .connect()   ->  ConnectedNatsBroker     живое соединение; подписки и издатели
  .shutdown()  ->  ClosedNatsBroker        конечный свидетель со снятыми счётчиками
```

`shutdown` поглощает подключённого брокера, поэтому публикация или подписка, написанная после него,
не компилируется. Издатель, выданный раньше, работает с тем же соединением, поэтому, как только
соединение закрыто, каждая публикация через него возвращает `NatsError::Closed`.

Учётные данные, TLS и остальная настройка клиента - это параметры `async_nats::ConnectOptions`, а
`NatsBroker::with_options` присоединяет их к брокеру. Клиент, созданный вне фреймворка, становится
подключённым брокером через `ConnectedNatsBroker::from_client`.

## Подписка Core NATS {#core-subscription}

Обработчик `#[subscriber("subject")]` привязывается к субъекту NATS:

```rust
--8<-- "crates/ruststream-nats/examples/nats_core.rs:handler"
```

Смонтируйте его внутри `with_broker`:

```rust
--8<-- "crates/ruststream-nats/examples/nats_core.rs:app"
```

`CoreSubject` - та же подписка с настройками, какие есть у Core NATS, а есть у него одна: очередь,
которая отдаёт каждое сообщение одному участнику, а не всем сразу. Читать много субъектов сразу -
это `CoreWildcard::new("orders.*")`: та же очередь и шаблоны `*` и `>`. Это разные типы, потому что
в шаблон нельзя опубликовать, а именно это решает, куда уйдёт отложенный повтор; см.
[Подтверждение и отложенный повтор](#acknowledgement-and-delayed-retry).

## Durable-консьюмер JetStream {#jetstream-durable-consumer}

Чтобы вместо этого читать из JetStream, назовите источник в атрибуте `#[subscriber(..)]` через
`JetStreamSubject`: субъект для чтения, стрим, который его хранит, и durable-консьюмер, позиция
которого переживает перезапуск.

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:handler"
```

В определении уже задан собственный источник, поэтому монтирование - обычный `include`:

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:mount"
```

Эту пару и генерирует заготовка `nats-js` из CLI.

Кроме `durable`, в `JetStreamSubject` задаются `filter_subject`, `ack_wait`, `max_ack_pending`,
`deliver_policy` и `pull_expires` (сколько один pull-запрос ждёт, прежде чем вернуться с тем, что
набралось). Балансировка нагрузки в Core NATS - это `CoreSubject::queue_group`. Общих настроек у
двух типов нет, поэтому настройка, указанная не на той модели, не компилируется.

`JetStreamSubject` - самостоятельный источник подписки, поэтому путь без макросов принимает его как
есть: `subscriber(JetStreamSubject::new("orders.*", "ORDERS"), body)` строит то же самое
определение. Контракт тела на этом пути описан в разделе
[Подписчики](https://docs.rs/ruststream/latest/ruststream/runtime/index.html#subscribers) справочника
фреймворка.

### Пакеты {#batches}

Обработчик, который принимает `&[T]`, получает пакет:

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:batch"
```

Точка монтирования добавляет размер пакета:

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:batch_mount"
```

На JetStream это число - размер пакета в pull-запросе: один пакет - это один `fetch` не более чем
на шесть сообщений, а `pull_expires` закрывает его раньше, когда за это время пришло меньше. В Core
NATS пакета при передаче нет, поэтому пакет собирает на клиенте адаптер `BufferedSubscriber` из
фреймворка, и неполный пакет закрывается через 10 мс после первой доставки.

Размер относится к регистрации, а не к подписке, поэтому в `JetStreamSubject` задано время
(`pull_expires`), а не количество.

### Подтверждение и отложенный повтор {#acknowledgement-and-delayed-retry}

Доставка JetStream завершается на сервере: `HandlerOutcome::ack()` подтверждает её,
`HandlerOutcome::retry()` отправляет отрицательное подтверждение, `HandlerOutcome::drop()`
прекращает её. `HandlerOutcome::retry_after(delay)` кладёт задержку в само отрицательное
подтверждение, поэтому сервер держит сообщение столько времени, а затем доставляет его повторно на
том же консьюмере, с прежним номером в стриме и прежним счётчиком доставок.

В Core NATS подтверждений нет вообще: доставка Core возвращает `AckError::Unsupported`, а
`retry_after` там превращается в копию - когда задержка вышла, фреймворк публикует сообщение заново.

Сколько доставок получает одно сообщение и куда оно уходит, когда они кончились, объявляют в точке
монтирования:

```rust
--8<-- "crates/ruststream-nats/examples/nats_retry.rs:declaration"
```

`max_attempts(n)` считает и первую доставку. На консьюмере JetStream читают счётчик самого сервера,
поэтому истёкший `ack_wait` тоже идёт в счёт; на субъекте Core фреймворк считает опубликованные им
копии, в заголовке `x-ruststream-retry-count`. `dead_letter(субъект)` - куда публикуется исчерпанная
доставка, телом и заголовками такой, какой пришла.

Собственного механизма мёртвых писем у NATS нет. `max_deliver` в JetStream ограничивает число
доставок, но отправить последнюю ему некуда, поэтому крейт не переносит объявление на него, и на
обеих моделях работает путь самого фреймворка.

Куда уйдёт копия - единственное, на что три подписки отвечают по-разному:

| Подписка | Что читает | Куда уходит копия |
| --- | --- | --- |
| `CoreSubject` | один субъект | в этот же субъект |
| `CoreWildcard` | много субъектов | в субъект, названный в точке монтирования |
| `JetStreamSubject` | стрим, через консьюмер | никуда: сообщение держит сервер |

Шаблон совпадает при доставке и отвергается при публикации, поэтому подписка `CoreWildcard` не может
сказать, куда копия придёт к ней снова. Это говорит точка монтирования:

```rust
--8<-- "crates/ruststream-nats/examples/nats_retry.rs:wildcard"
```

`.to(субъект)` - один фиксированный субъект; преобразование с `Names` выбирает его на каждую
доставку, по той доставке, копией которой он является. Регистрация по шаблону, которая не называет
ни того, ни другого, отказывается стартовать: сервис сообщает об этом сразу, а не теряет каждое
отложенное сообщение уже на ходу.

`out_retry(политика)` называет издателя, через которого уходит копия, и нужен только там, где копии
нужен свой издатель: без него они уходят через обычного издателя брокера. Эта позиция - слот `Out`,
поэтому за ней идут шаги слота: `.transform(..)` помечает каждую копию, `.map_publisher(..)` задаёт
то, что несёт сам издатель. Копия едет теми байтами, с которыми пришла доставка, поэтому названный
здесь кодек ничего не кодирует. На консьюмере JetStream копий нет вовсе, и `out_retry` там называет
только издателя, через которого уходит исчерпанная доставка.

## Публикация {#publishing}

Политика публикации, которую вы назвали, выбирает транспорт:

- `NatsPublish` конструирует `NatsPublisher`: обычная публикация Core NATS, без ожидания ответа
  сервера, и на том же живом значении - совместимость `RequestReply`. Это ещё и политика
  публикации брокера по умолчанию, поэтому отвечающий обработчик, смонтированный без
  `.out_reply(..)`, отвечает через неё. В прелюдии крейта она называется `Publish`.
- `JetStreamPublish` конструирует `JetStreamPublisher`: каждая публикация ждёт подтверждения от
  стрима, поэтому сообщение, которое стрим отверг, возвращает ошибку, а не пропадает молча.
  `publish_ack` возвращает само подтверждение: стрим, номер и признак того, что окно дедупликации
  узнало сообщение. Эта же политика через `expect_stream` называет стрим, которым должен
  обслуживаться субъект, и публикация, ушедшая в другой стрим, отвергается.

Обработчик на консьюмере JetStream отвечает, возвращая значение:

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:reply"
```

Точка монтирования называет политику, поэтому сообщения-подтверждения одного обработчика уходят в
стрим, который их подтверждает, а остальной сервис продолжает публиковать через Core NATS:

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:reply_mount"
```

Вне обработчика та же политика инстанцирует издателя на старте:

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:publish"
```

### Что одно сообщение JetStream заявляет о себе {#what-one-jetstream-message-states-about-itself}

Идентификатор для дедупликации и ожидаемая позиция в стриме описывают одно сообщение, а не
издателя, поэтому они передаются вместе с публикацией. Значение, в котором они хранятся, -
`JetStreamOptions`, и заполняет его билдер публикации:

| Шаг | Поле протокола | Что с ним делает сервер |
| --- | --- | --- |
| `message_id(id)` | `Nats-Msg-Id` | Сохраняет повтор внутри окна дедупликации только один раз. |
| `expect_last_sequence(n)` | `Nats-Expected-Last-Sequence` | Отвергает публикацию, если стрим не на `n`. |
| `expect_last_subject_sequence(n)` | `Nats-Expected-Last-Subject-Sequence` | То же самое, но для собственного субъекта этого сообщения. |
| `expect_last_message_id(id)` | `Nats-Expected-Last-Msg-Id` | Отвергает публикацию, если последний `Nats-Msg-Id` в стриме не равен `id`. |

Тело вызывает шаг на билдере публикации:

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:options"
```

Это единственное место, где тело обработчика называет брокера. Шаги приходят из
`ruststream_nats::prelude`, а слот ограничен `Out<impl Publisher<Options = JetStreamOptions>,
Archive>`, поэтому сигнатура прямо говорит, что тело написано под JetStream. Тело, которое
публикует без шага, оставляет прелюдию фреймворка и монтируется на любой брокер.

Точка монтирования по-прежнему называет политику, и эти два выбора не пересекаются: в какой стрим
пишет издатель - слово точки монтирования, а что одно сообщение утверждает о состоянии стрима -
слово тела.

```rust
--8<-- "crates/ruststream-nats/examples/nats_jetstream.rs:options_mount"
```

Шаг - это позиция на билдере, а не обёртка вокруг издателя, поэтому законченная им публикация
всё равно уходит через собственную запись точки монтирования, с тем кодеком, который эта запись
назвала.

В Core NATS собственных настроек для отдельного сообщения нет: сообщение Core - это субъект,
полезная нагрузка и заголовки, поэтому `NatsPublisher` объявляет `Options = ()`, и перечисленных
выше шагов на билдере над ним в области видимости нет.

## Запрос-ответ {#request-reply}

NATS сопоставляет ответы нативно, поэтому `NatsPublisher` реализует совместимость `RequestReply`, а
прелюдия крейта её реэкспортирует. `request(msg, timeout)` публикует сообщение вместе с инбоксом
для ответа и возвращает сообщение-ответ либо ошибку таймаута, когда за отведённое время никто не
ответил:

```rust
use std::time::Duration;

use ruststream::OutgoingMessage;
use ruststream_nats::prelude::*;

--8<-- "crates/ruststream-nats/examples/nats_request_reply.rs:request"
```

Ответить на него может любая отвечающая сторона NATS: другой сервис или `nats reply questions
'pong'` из CLI. Готовая к запуску программа -
[`examples/nats_request_reply.rs`](https://github.com/powersemmi/ruststream-nats/blob/main/crates/ruststream-nats/examples/nats_request_reply.rs).

У входящего запроса инбокс для ответа записан в известном заголовке `reply-to`, поэтому отвечающая
сторона читает `ctx.headers().reply_to()` и публикует ответ в этот субъект через внедрённого
издателя.

## Документ AsyncAPI {#the-asyncapi-document}

`asyncapi gen` пишет документ, который публикует сервис, а фича `asyncapi` - то, что позволяет этому
крейту заполнить в нём части, известные только NATS:

```toml
ruststream-nats = { version = "0.7", features = ["asyncapi"] }
```

В спецификации AsyncAPI у привязки `nats` ровно одно поле: очередь, на операции приёма. Подписка,
которая в неё входит, сообщает её, а подписка без очереди оставляет документ в покое, а не добавляет
пустой объект:

```rust
--8<-- "crates/ruststream-nats/tests/asyncapi_nats.rs:queue_group"
```

Всё, чем настроен консьюмер JetStream, в этой привязке поля не имеет, а ключи протоколов - закрытый
список, поэтому оно едет под `x-ruststream-jetstream` на канале. Расширение - не привязка, и версии
`bindingVersion` оно не несёт:

```rust
--8<-- "crates/ruststream-nats/tests/asyncapi_nats.rs:consumer"
```

Издатель, которому нужен определённый стрим (`JetStreamPublish::default().expect_stream("ORDERS")`),
сообщает этот стрим под тем же ключом, а рядом называет субъект, который этот стрим обязан
обслуживать. Субъект здесь - то назначение, которое разрешила точка монтирования, поэтому требование
читается одним утверждением, а не двумя половинами, которые читатель складывает сам:

```rust
--8<-- "crates/ruststream-nats/tests/asyncapi_nats.rs:publish_stream"
```

Ответ говорит, где клиент читает субъект, куда уйдёт ответ. NATS везёт инбокс запроса в поле
протокола, которое крейт показывает как заголовок `reply-to`, - это и есть выражение, которое
сообщает документ, а собственного адреса у канала тогда нет, потому что адрес свой на каждый запрос:

```rust
--8<-- "crates/ruststream-nats/tests/asyncapi_nats.rs:reply_address"
```

Двух вещей здесь нет намеренно. Учётных данных: пароль, записанный в `nats://svc:secret@host`,
дальше соединения не идёт, и сервер в документе - это только хост и порт. Версии клиентского
протокола NATS: сервер сообщает её уже на соединении, а документ строится до того, как куда-либо
позвонили, поэтому её читают из `ConnectedNatsBroker::server_spec`.

## Совместимости {#capabilities}

Какие из необязательных трейтов-совместимостей фреймворка этот брокер реализует нативно:

| Совместимость | Нативно | Примечания |
| --- | --- | --- |
| `Subscribe` | да | Подписывается по субъекту через `CoreSubject`, поэтому голый `#[subscriber("orders.created")]` - это один субъект. `CoreWildcard` читает шаблон, а `JetStreamSubject` - стрим через консьюмер. |
| `BatchSubscriber` | да | На JetStream один пакет - это один pull-`fetch` не более чем на `batch(n)` из точки монтирования, ограниченный `pull_expires`. В Core NATS пакета при передаче нет, поэтому пакет собирает на клиенте адаптер `BufferedSubscriber` из фреймворка. См. [Пакеты](#batches). |
| `TransactionalPublisher` | нет | Ни у одной из моделей нет транзакции на несколько сообщений; публикация в JetStream подтверждается по одному сообщению. |
| `OwnedTransactions` | нет | По той же причине: владеть нечем, транзакции нет. |
| `RequestReply` | да | `NatsPublisher` публикует с нативным инбоксом для ответа и возвращает ответ. См. [Запрос-ответ](#request-reply). |
| `Partitioned` | да | Нативных партиций у NATS нет, поэтому отправитель кладёт ключ в заголовок `nats-partition-key`, а партиции воркеров `workers(n, by_key)` в рантайме читают его оттуда. |
| `Seekable` + `Positioned` | нет | `deliver_policy` выбирает, с какого места начинает только что созданный консьюмер JetStream; живую подписку не перематывают. |
| `DescribeServer` | да | Сообщает хост и порт каждого настроенного адреса, поэтому учётные данные, записанные в URL, в документ AsyncAPI не попадают. См. [Документ AsyncAPI](#the-asyncapi-document). |

## Тестирование {#testing}

Фича `testing` поставляет `NatsTestBroker`: внутрипроцессный транспорт с настоящим сопоставлением
субъектов NATS (шаблоны `*` и `>`), передачей заголовков и запросом-ответом, без `nats-server` и
без docker. На нём работает обвязка `TestApp`: публикуйте вход тем же билдером, которым публикует
сервис, и обвязка сообщит, что получил обработчик, что он опубликовал и чем завершилась доставка.
Обвязка и её проверки описаны в справочнике фреймворка, в модуле
[`ruststream::testing`](https://docs.rs/ruststream/latest/ruststream/testing/index.html).

Шесть особенностей NATS сохраняются внутри процесса, поэтому обработчик, который ими пользуется,
тестируется без сервера:

- Источник `JetStreamSubject` разрешается и здесь; маршрутизацию задаёт шаблон субъекта.
- Конкурирующие консьюмеры конкурируют. Группа `queue_group` в Core NATS и подписки с общим
  `durable` в `JetStream` берут каждое сообщение по очереди, а не получают по копии каждая -
  ровно так сервер отдаёт его одному члену набора; подписка вне такого набора по-прежнему получает
  каждое подходящее сообщение. Без этого тест позволил бы двум воркерам выполнить одну и ту же работу и
  засчитал бы это за успех, поэтому поведение воспроизведено, а не оговорено в документации.
  Ротация здесь детерминированная, поэтому тест может проверить, какой именно член отработал;
  сервер выбирает члена сам, а общее у обоих то, что группа видит каждое сообщение один раз.
- Политики публикации - те же, что в продакшене. `NatsPublish` и `JetStreamPublish` конструируют
  издателя и на тестовом брокере, а `NatsPublish` - его политика по умолчанию, поэтому файл с
  маршрутами монтируется без изменений: `b.include(confirm).out_reply(Publish)` и
  `b.include(audit).out(Audit, JetStreamPublish::default())` означают на обоих брокерах одно и то
  же. Собственной политики тестового транспорта, которую надо было бы подставить, нет. У каждой
  живой формы ровно те же совместимости, что и у её продакшен-аналога - `Publisher` и
  `RequestReply` для Core, только `Publisher` для `JetStream`, - поэтому слот, который
  компилируется здесь, компилируется и против сервера.
- То, что одно сообщение заявляет о себе, доходит и здесь. Шаги пишут тот же `JetStreamOptions`, а
  транспорт превращает его в те же заголовки протокола, которые пишет настоящий клиент, поэтому
  тест читает любую из двух сторон:

    ```rust
    --8<-- "crates/ruststream-nats/tests/handlers.rs:options_assert"
    ```

    `assert_options_default()` - зеркальная проверка для публикации, которая не назвала ни одного
    шага.

- Обработчик, который привязывает нативные метаданные `JetStream` по ключу из
  `ruststream_nats::context`, монтируется, и каждый ключ читается как `None`, ровно как на доставке
  Core.
- Отложенный повтор идёт тем путём, который ему положен по модели. Доставка через
  `JetStreamSubject` придерживает сообщение сама и считает свои доставки, поэтому объявленный
  предел читает здесь то же число, что и на сервере; доставке на субъекте Core придерживать его
  нечем, поэтому копия уходит через издателя повтора этой регистрации, вместе с привязанными там
  преобразованиями. Таймером в обоих случаях владеет обвязка, поэтому `tb.advance(delay)`
  запускает повтор при остановленных часах, а исчерпанная доставка приходит на объявленный субъект
  мёртвых писем, где её читает `tb.published::<T>(..)`.

Сама семантика `JetStream` (курсор durable-консьюмера и его восстановление, повторная доставка по
`ack_wait`, хранение, что на самом деле делают метаданные и задержка на стороне сервера) не
моделируется; проверяйте её на настоящем сервере, включив такие тесты переменной `NATS_TEST_URL`.
Общий `durable` воспроизводит то, что его подписки конкурируют, а не то, где остановился консьюмер.
На стороне публикации из моделирования исключён стрим: внутрипроцессный транспорт - это одна среда
сопоставления субъектов Core, поэтому монтирование `JetStreamPublish` маршрутизирует, но
подтверждения, которого можно было бы дождаться, здесь нет, и состояния стрима, с которым
сверяется ожидание, тоже нет. Публикация, нарушающая ожидание, здесь проходит там, где сервер
отверг бы её, поэтому цепочка с оптимистическим управлением параллелизмом ничего не доказывает,
пока не выполнена вживую.

Как этот брокер реализует контракт изнутри, описано в
[разборе примера](https://powersemmi.github.io/ruststream/latest/broker-authors/example-nats/) в
документации фреймворка.
